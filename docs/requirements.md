# Chunking Studio 요구사항 정의서

> 버전: v0.2 · 작성일: 2026-11-11 · 변경: 미결 사항 #2·#3·#4 결정 반영 (10장 참고)

## 0. 개요

Chunking Studio는 RAG 파이프라인의 **청킹 품질을 실험·검증·운영**하기 위한 UI 기반 솔루션이다.

- 런타임 입력은 **관리자가 등록한 Parser의 파싱 결과**이다. Studio는 운영 시 Parser를 실행하지 않고 결과만 수신한다.
- 단, **UI 테스트 시에는 Studio가 등록된 Parser API를 직접 호출**해 샘플 문서를 파싱하고 결과를 즉시 확인한다.
- 청킹은 **LLM 기반 시멘틱 청킹**을 중심으로 하며, 사용자는 **프롬프트를 수정해가며 결과를 UI에서 확인**한다.
- LLM은 **경계(Element ID 범위)만 반환**하며, 청크 본문은 항상 원본 Element 텍스트로 조립한다.
- 사용 LLM은 **선택 가능**하며, 상용 API와 **오픈소스 모델(자체 서빙)**을 모두 지원한다.
- 청킹 결과는 **RAGAS로 자동 평가**하며, 평가 데이터셋은 **LLM으로 자동 생성**한다.

### 전체 흐름

```
[관리자] Parser 등록 ──▶ Parser Registry
                             │
[운영] 파싱 결과 유입(수신) ─┤──▶ 표준 스키마 변환 ──▶ 파싱 결과 뷰어
[테스트] 샘플 문서 업로드 ──▶ Parser API 직접 호출 ─┘     │
                                                       ▼
                         LLM 시멘틱 청킹 (Prompt Playground) ◀── 프롬프트 수정 반복
                                                       │
                     데이터셋 자동 생성 ──▶ RAGAS 자동 평가 ──▶ 결과 대시보드 / 승격 게이트
```

### 역할

| 역할 | 권한 |
|---|---|
| 관리자 | Parser 등록/수정/비활성화, 어댑터 관리, 권한·모델·예산 설정, 프롬프트 production 승인, 모니터링 |
| 사용자 | 허용된 Parser 결과 조회·비교, 테스트 문서 업로드, 청킹 프롬프트 실험, 평가 실행, 데이터셋 검수 |
| 뷰어(선택) | 조회 전용 |

## 2. 표준 파싱 결과 스키마

모든 UI 표시·비교·청킹의 기준이 되는 공통 스키마.

- **Document**: doc_id, 원본 파일 참조, 파일 해시, parser_id, parser_version, 파싱 시각, 설정값
- **Page**: page_no, width, height, 페이지 이미지 참조
- **Element**: element_id, type(title/heading/paragraph/list/table/figure/caption/header/footer/footnote …), text, page, bbox, reading_order, level, parent_id, confidence
- **Table**: 셀 구조(row, col, rowspan, colspan), HTML/Markdown 표현
- **Figure**: 이미지 참조, 캡션, VLM 설명(선택)
- **extra**: Parser 고유 필드 보존용 확장 영역

## 5. LLM 시멘틱 청킹

### 5.1 프롬프트 관리

| ID | 요구사항 |
|---|---|
| PM-01 | System/User 프롬프트 템플릿 편집기, 변수(`{{elements}}`, `{{section_path}}`, `{{max_tokens}}`, `{{doc_type}}`) 하이라이트·자동완성 |
| PM-02 | Few-shot 예시(입력 → 기대 청크) 별도 관리 및 삽입 |
| PM-03 | 출력 JSON Schema 정의 (Structured output / JSON mode) |
| PM-04 | 저장 시 버전 생성, diff, fork, 롤백, 수정 메모 |
| PM-05 | 상태 태그: draft → testing → approved → production (production 승격은 관리자 승인) |
| PM-06 | 문서 유형별 프롬프트 매핑 |

### 5.2 모델 설정

| ID | 요구사항 |
|---|---|
| MS-01 | LLM Gateway를 통해 실험·프롬프트별로 모델을 선택. 상용 API와 오픈소스 모델 모두 지원 |
| MS-02 | temperature, max_tokens, top_p, seed, 재시도 횟수 |
| MS-03 | 동일 프롬프트로 모델 간 결과 비교 (상용 vs 오픈소스 포함) |
| MS-04 | 모델 레지스트리(관리자): 공급자 유형 등록 — 상용 API(OpenAI·Anthropic·Azure 등), OpenAI 호환 엔드포인트, 오픈소스 서빙(vLLM·TGI·SGLang·Ollama 등) |
| MS-05 | 모델별 capability 메타데이터: 컨텍스트 길이, 최대 출력 토큰, Structured output 지원 방식, 토크나이저 |
| MS-06 | Structured output 계층적 지원: 네이티브 JSON Schema → JSON mode → 제약 디코딩(guided decoding/grammar) → 프롬프트 지시 + repair. 모델 capability에 따라 자동 선택 |
| MS-07 | 모델 컨텍스트 길이에 맞춰 윈도우 크기 자동 조정 (CI-02 연동) |
| MS-08 | 모델별 토크나이저로 토큰 수 계산, 비용 산정: 상용은 토큰 단가, 자체 서빙은 단가 0 또는 GPU 시간 기준 |
| MS-09 | 모델 헬스체크, 지연시간·오류율 모니터링, 프로젝트별 사용 가능 모델 제한 |
| MS-10 | 폐쇄망: 외부 API 차단 시 자체 서빙 모델만 노출 |

### 5.3 입력 구성

| ID | 요구사항 |
|---|---|

|---|---|
| EV-01 | 실험별 임시 Vector 인덱스 자동 생성·정리 |

| 구분 | 지표 |
|---|---|
| 검색 | Context Precision, Context Recall, Context Entities Recall |

| 강건성 | Noise Sensitivity |
| 보조(비LLM) | Recall@k, MRR, Hit rate (정답 Element ↔ 청크 Lineage 매핑) |

- 프로젝트별 지표 세트 선택, 가중치 기반 종합 점수

### 6.3 자동 실행

| ID | 요구사항 |
|---|---|

| ET-02 | 실험 매트릭스 (프롬프트 × 모델 × Top-k) 일괄 평가, 사전 비용 예측 |
| ET-03 | 스케줄 기반 production 회귀 평가 |

### 6.5 신뢰성

- Judge LLM·임베딩은 청킹/생성용과 분리·고정
- 반복 실행 옵션, 평균·신뢰구간 표시
- RAGAS 라이브러리 버전 고정 및 결과에 기록
- 채점 결과 캐싱, 비동기 병렬 처리, rate limit, 실험당 비용 상한
- 질문 단위 원시 결과 전체 저장

## 7. 평가 데이터셋 자동 생성 (LLM)

### 7.1 소스 선택

| ID | 요구사항 |
|---|---|
| DG-01 | 생성 범위: 문서 전체 / 문서 유형 / 섹션·페이지 |
| DG-02 | 문서·섹션 커버리지 균형 샘플링 |
| DG-03 | Element 타입 분포 지정 (본문·표·목록·캡션) |
| DG-04 | 목표 생성 개수 설정 |

### 7.2 생성 방식

- RAGAS TestsetGenerator 연동 (지식 그래프, 페르소나, Query Synthesizer)
- Studio 자체 프롬프트 파이프라인 (프롬프트 관리 기능 공유)
- 생성용 LLM은 청킹·생성·Judge용과 분리

### 7.3 질문 유형·분포

사실형, 정의·설명형, 절차형, 수치·표 기반, 비교형, 조건·예외형, 다중 홉, 답변 불가형

- 유형별 비율, 난이도, 페르소나 설정
- 질의 스타일 다양화: 구어체, 키워드형, 오탈자·축약어
- 운영 질의 로그 기반 Few-shot (가능 시)

### 7.4 결과 스키마

question, reference_answer, reference_contexts, **source_element_ids / page / bbox** (청크 독립적 정답 위치), type, difficulty, persona, multi_hop, 생성 메타데이터(모델·프롬프트 버전·파라미터·시각·필터 점수)

### 7.5 자동 품질 필터

| 검사 | 내용 |
|---|---|
| 답변 가능성 | 정답이 근거로 뒷받침되는지 |
| 자기완결성 | "이 문서에서" 등 맥락 의존 질문 제거 |
| 쉬움 필터 | 원문 복사형 질문 제거 (어휘 중복도) |
| 중복 제거 | 임베딩 유사도 기반 |
| 형식 검증 | 길이, 언어, JSON 스키마 |
| LLM 비평가 | 명확성·현실성·난이도 점수화 |

- 탈락 사유 기록

### 7.6 검수 UI

- 유형·난이도·점수·상태 필터 목록
- 근거 Element 원문 하이라이트 상세 뷰
- 승인/수정/반려(사유 태그), 일괄 처리
- 샘플 검수 모드 (무작위 N%)
- 커버리지 맵, 분포, 합격률 통계

### 7.7 버전 및 활용

- 검수 완료 세트 버전 확정, 변경 이력
- **dev / test(holdout) 분리**: 튜닝은 dev, 승격 게이트는 test → 과적합 방지
- 원본 문서 변경 시 영향 질문 stale 표시 및 재생성·재검수
- RAGAS 호환 포맷(JSONL/CSV) 내보내기 및 외부 데이터셋 import
